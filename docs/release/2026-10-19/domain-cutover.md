# План переключения домена — НЕ применён

Подготовка: 19.10.2026. Выпуск требует отдельного GO владельца. Этот документ не является автоматическим deploy и не разрешает изменения production.

## Проверенное исходное состояние

- Основной yaclinic.ru и www обслуживаются прежним сервером; new.yaclinic.ru остаётся стендом.
- DNS не менялся. Актуальные значения и TTL сохранены в приватном пакете; это выборка записей, не полный экспорт зоны.
- Проверка будущих apex/www на сервере стенда с `curl --resolve`, без отключения TLS, завершилась ошибкой имени сертификата. До исправления HTTPS переключать DNS нельзя.
- Восстановление данных и файлов: [контрольная точка](backup-checkpoint.md). Полная HTTP-репетиция и свежая внешняя копия ещё не приняты.

## До окна выпуска

1. Назначить ответственного за окно и откат; получить отдельное разрешение на выпуск.
2. Зафиксировать контент. Снять финальные приватные копии старого и нового сайтов, конфигураций и полной DNS-зоны. Проверить внешнее хранение и контрольные суммы.
3. Подготовить отдельную production-копию с отдельной БД и закрытым доступом. Не использовать одну изменяемую БД для стенда и production.
4. Для HTTP-репетиции исключить внешнюю сеть, cron, почту, webhooks и SQNS до запуска WordPress. Исходный восстановленный wp-config.php сначала безопасно перенастроить.
5. Инвентаризировать фоновые задания, интеграции и кэши. Только один экземпляр может доставлять обращения после выпуска.
6. Назначение исполнителей остаётся отдельному сервису. Не менять его настройки и не объявлять запись принятой до серверной проверки интеграции. Выпуск с неработающей записью отдельно не согласован.
7. Подготовить валидные HTTPS-сертификаты для apex/www и проверить цепочку без `-k` до смены DNS.

## Изменения только будущей production-копии

1. Сохранить исходники и хеши изменяемых объектов; подготовить точечные diff и возврат.
2. Установить home/siteurl на `https://yaclinic.ru`; проверить WP_HOME/WP_SITEURL и определение HTTPS за прокси.
3. Заменить URL стенда сериализационно-безопасным средством: явный scope таблиц/столбцов → dry-run → просмотр замен → применение → readback. Не применять SQL REPLACE к сериализованным Elementor/ACF, не менять GUID, не выполнять all-tables/network-wide. Наличие инструмента ещё нужно подтвердить; установка этим этапом не выполнялась.
4. Отдельно проверить доменные guards в активном коде. Минимум snippets 32–45 привязаны к new.yaclinic.ru. Снять свежий код CMS и подготовить ограниченный diff для точного основного host только в production-копии. Стенд сохранить без изменений; не удалять guards глобально.
5. Сохранить контекст услуги/врача, 14 согласованных старых маршрутов и якорь пилинга головы. Сохранить GET/HEAD, точные пути, query allowlist и запрет открытого редиректа.
6. Использовать актуальную согласованную карту из 171 строки, а не весь черновой redirect-plan. Исключённые страницы не получают автоматический 410 или произвольный 301. Старые медицинские тексты не возвращать.
7. Подготовить отдельные vhost apex/www, не изменяя стенд и dashboard. www → HTTPS apex с сохранением пути/query. Проверить конфигурацию перед reload.
8. До выпуска оставить копию закрытой и неиндексируемой. При выпуске снять noindex только у production; сохранить noindex стенда. Проверить robots/X-Robots-Tag, self-canonical и фактический sitemap. Отсутствующий canonical каталога — отдельная проверка, а не автоматически исправленный факт.
9. Спорные FAQ публиковать только после проверки назначенным врачом. Отложенная копия лицензии не означает юридическую приёмку сайта.

## Приёмка до изменения DNS

- Проверять реальный будущий vhost с валидным TLS через host override; не обходить ошибки сертификата.
- Главная, все опубликованные услуги/врачи, каталог/фильтры, переходы и возврат, поиск, формы и контекст записи, документы/50 оригиналов, медиа/byte-range видео, единый просмотрщик, контакты/маршрут, отзывы из 4 источников, multilink/serial.
- Viewport 360/390/768/1440; эмуляция не заменяет физические устройства.
- Каждый согласованный старый URL: GET/HEAD 301 → правильный URL 200, UTM/yclid сохранены, циклов нет. POST/API/медиа и неизвестные/повторные query проверять отдельно в изолированной среде, без реальных заявок.
- Старые 60 проверок стенда не заменяют приёмку будущего production-vhost.

## Окно выпуска после отдельного GO

1. Повторно сверить финальную версию, копии, DNS и новые обращения.
2. Менять только согласованные apex/www A. При появлении AAAA/CNAME остановиться и уточнить пакет. MX/TXT/NS, new/dashboard/lp не менять.
3. Проверить авторитетные и внешние DNS, TLS, редиректы, 200/404/5xx, индексацию, медиа и формы. Синтетический тест записи — отдельный разрешённый сценарий с серверным readback, не только успехом окна.
4. Наблюдать доступность, ошибки и обращения сразу после переключения и на следующий день. Не передавать пациентские данные в технические отчёты.

## Откат

Остановка: ошибка TLS, петли, массовые 404/5xx, неработающая запись, потеря контекста, дубли доставки, недоступные документы или неверная индексация.

До смены DNS: отменить только изменения будущей production-копии. Не откатывать БД стенда.

После смены DNS: сохранить новые обращения/журналы обоих серверов приватно; остановить дубли доставки согласованным способом; вернуть только нужные DNS-записи из свежего экспорта; проверить старый сайт. Учесть трафик из DNS-кэшей. Не восстанавливать старую БД поверх новых заявок и не удалять новую копию до сверки обращений и доставки без дублей.

RTO/RPO не установлены: время полной HTTP-репетиции и внешнее восстановление пока не измерены.

Метод: [WordPress migration](https://developer.wordpress.org/advanced-administration/upgrade/migrating/), [WP-CLI search-replace](https://developer.wordpress.org/cli/commands/search-replace/). Ссылки не подтверждают установку инструментов или выполнение переключения.
