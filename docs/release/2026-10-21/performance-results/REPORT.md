# Пять оптимизаций new.yaclinic.ru — результат 21 октября 2026

## Итог и границы

Все пять направлений применены **только на стенде**. Production, домен, DNS, сертификаты и конфигурация Nginx/FPM не менялись. Цены, карточки, публичные тексты и оригинальные изображения сохранены. Назначение исполнителей не меняли. Реальные записи и обратные звонки не отправляли.

Основной измеренный выигрыш: повторная серверная выдача публичных страниц из короткого кеша, меньше повторного CSS и меньше ресурсов до первого действия. Это **не доказательство**, что полная загрузка любой страницы ускорилась на тот же процент. Холодная генерация Elementor и авторизованные запросы остаются медленными.

Рабочая ветка Direct_Yabloko: `codex/direct-workbench-stage0`, без remote; чужие изменения сохранены. Проверенные контрольные точки отправлены в существующий репозиторий сайта `sahchandansah1201-glitch/yabloko-bloom`, ветка `main`, только в `docs/release/2026-10-21/`. Эти коммиты сами по себе не публикуют React-приложение.

Одинаковый протокол: 13 URL × 3 последовательных HTTPS GET, без cookies, gzip, без обхода TLS, без параллельной нагрузки. TTFB включает сеть/TLS и серверный ответ. Это не нагрузочный тест и не полевые Core Web Vitals.

Финал: `after-five/http.json`, UTC 17:45–17:46, **39/39 HTTP 200**, у каждого маршрута один MISS и два HIT. Сырые первые данные не перезаписывались. ## Почему сервер отвечал долго

Один диагностический запрос через реальный локальный PHP-FPM/FastCGI на стенде, не CLI-рендер и не статистическая серия:

- Прайс: 3733,52 мс генерации; 404 SQL-запроса суммарно 192,91 мс.
- 218 рендеров шаблона строки 2913: 2527,22 мс суммарно. Внешний шаблон 2903: 2993,24 мс **включает** строки, эти числа нельзя складывать.
- Внешних HTTP-вызовов в этом запросе: 0; пиковая память около 62 МиБ.
- OPcache включён, около 99,82% hit, 87,5 МБ занято / 46,8 МБ свободно, без рестартов.

Факт: основная стоимость этого запроса — повторный Elementor-рендер строк, не SQL и не заполненный OPcache. Статистика очереди FPM/нагрузки в эту одиночную пробу не входит. Точечная замена серверного рендера прайса остаётся возможным следующим этапом; здесь не предпринималась рискованная перепись карточек.

### Что не доказано

Гостевые LCP/INP/CLS и полная загрузка на физическом iOS/Android, медленной мобильной сети, полевой CrUX не измерены. Browser bootstrapping заблокирован локальной подписью native dependency; защиту не обходили. Существующая сессия WordPress не удалялась ради теста.

Попытка сопоставимого браузерного прогона 390 px / CPU×4 / cache off дала для авторизованной главной load **16,408 с** против **8,511 с** в первом авторизованном одиночном замере; TTFB 8,185 с. Это не ускорение, не гостевая оценка и не статистически достоверный before/after. Полная серия не завершена из-за тайм-аутов. Поэтому результат заявлен только как сокращение ресурсов и гостевого серверного ответа с прогретым кешем, а не как общий процент ускорения интерфейса.

Сетевой сбой/retry покрыт изолированным тестом; искусственный обрыв в живом браузере не выполнялся. Заявка не отправлялась, серверное создание записи заново не проверялось.

## Исправленные проблемы внедрения

1. Elementor переиспользовал HTML, первоначальный attachment filter не менял картинки. Перенесён на итоговый frontend content; currentSrc проверен.
2. Папка новых JS из-за umask была недоступна web-серверу. Исправлены права только этой новой папки; fail-open до исправления оставлял исходный виджет.
3. Полное удержание HTML в первой версии кеша выявило 502 на акне (`upstream sent too big header`, существующие ACF warnings в stderr). Исправлено сохранением нормального streaming с копией для кеша, без правки Nginx и без подавления предупреждений. Неудачный прогон сохранён отдельно в `after-five-pre-streaming-failed/`, исключён из финальных расчётов.
4. Промежуточная версия snippet 53 получила повторное объявление helper при validate+execute, Code Snippets автоматически её отключил. Защита helper + тест повторного include + проверка actual SHA перед точечным ремонтом восстановили активность. После ремонта финальные серверные проверки пройдены.
5. `wp_json_encode(Snippet)` сериализовал защищённые свойства как `[]`. Такие промежуточные файлы **не считаются резервной копией**. Для ремонта сохранены явные поля code/id/active/scope; исходные plugin assets и валидные SQL-снимки сохранены приватно.
6. Перед финальной серверной перепроверкой тест случайно читал старый приватный asset-runtime.php, а не уже опубликованную guarded версию. Старый тест воспроизвёл fatal; приватный test fixture обновлён из финального файла, повтор — `ASSET_RUNTIME_4_CHECKS_OK`, `INTEGRITY_EXIT=0`. Публичный runtime при этом не менялся.

## Откат и остаточные риски

- Snippet 50: деактивировать только его, оставить прежний 49.
- Snippet 51: деактивировать только его, оригинальные PNG остаются на месте.
- Snippet 53: деактивировать только его — вернутся исходные plugin JS/CSS; snippet 52 не трогать.
- MU cache: убрать только `yaclinic-public-html-cache.php` из mu-plugins в существующую приватную backup-папку; затем проверить гостевые страницы и запись. Не откатывать всю БД и не удалять другие плагины.
- Файлы кеша/диагностика/SQL backup — вне webroot, не в Git. Installation receipts сверены. Установщики не запускать повторно без readback.
- Кеш не устраняет исходную дорогую генерацию; авторизованные/с cookies/query и cold MISS остаются отдельным направлением. Актуальность автоматических данных, которые обходят WordPress hooks, ограничена TTL 120 с.
- Hash guards потребуют пересборки derived assets после обновления SQNS/reviews; до неё штатный исходный вариант будет работать без этой оптимизации.
- Следующий полезный шаг — узкая оптимизация холодного серверного рендера прайса и отдельный гостевой браузерный замер. Полного релизного GO этот отчёт не выдаёт.
